Ты — модератор консенсус-панели проекта `dsgvo-check` (open-source CLI-сканер на TypeScript + Playwright, Apache-2.0; пассивно проверяет немецкие сайты на признаки нарушений DSGVO/TDDDG/DDG и базовые проблемы безопасности, роняет CI по порогу). Сегодня 2026-10-30. Твой результат станет единственным источником решений, по которому пишутся бриф, архитектура, спецификация проверок и план.

## Входные данные

- `specs/*.md` — идея, ТЗ (контракт), каталог проверок
- Раунд 1: `docs/consensus/round-1/*.md` (выжимка ресёрча, критик полноты, анализ ТЗ и red-team Codex); полные отчёты — `docs/01-research/*.md`
- Раунд 2, независимые предложения: `docs/consensus/round-2/claude-opus-5.5_proposal.md`, `claude-fable-5.1_proposal.md`, `codex-gpt-6.1-sol_proposal.md`, `codex-gpt-6.1-terra_proposal.md`
- Раунд 3, перекрёстная критика с голосованием по точкам D01–D27 (формулировки точек — в `docs/consensus/prompts/round-3_cross-critique.md`):
  - `docs/consensus/round-3/claude-fable-5.1_critique.md` — правовая линза
  - `docs/consensus/round-3/claude-opus-5.5_critique.md` — архитектурная линза
  - `docs/consensus/round-3/codex-gpt-6.1-sol_critique.md` — точность браузерного детекта
  - `docs/consensus/round-3/codex-gpt-6.1-terra_critique.md` — тесты, CI, безопасность

Прочитай целиком ТЗ, каталог и все четыре критики. Предложения и ресёрч открывай там, где критики спорят или ссылаются на конкретное место.

## Правила синтеза

1. Для каждой точки D01–D27 собери позиции: 4 предложения (раунд 2) и 4 голоса критиков (раунд 3).
2. Уровень согласия: **единогласно** (все 4 критика за один вариант), **большинство** (3 из 4), **спор** (2:2 или все разные).
3. Итоговое решение. При единогласии и большинстве бери выбор большинства, но если меньшинство нашло ошибку факта, права или ТЗ, она весит больше голосов: исправь решение и объясни почему. При споре реши сам по аргументам. Приоритет: ТЗ и право ЕС/Германии → корректность детекта (без ложных critical) → простота (YAGNI) → сроки.
4. Решение не может противоречить обязательным требованиям ТЗ. Если панель считает требование ТЗ ошибочным, оформи это как вопрос заказчику, а в решении держись ТЗ до ответа.
5. Ошибки, найденные критиками в предложениях, и факты, которые остались непроверенными, сведи в отдельные таблицы. Не переноси в итог непроверенный факт как проверенный.
6. Вопросы заказчику: объедини дубликаты из всех раундов и оставь только те, без которых нельзя начать этап или зафиксировать контракт. Для каждого — варианты, рекомендация панели и этап, к которому нужен ответ.

## Что выдать

Файл `docs/consensus/README.md`, Markdown на русском, немецкие термины как есть. Структура:

1. **Как шёл консенсус.** 4 раунда, модели, роли, ссылки на файлы. Коротко.
2. **Итоговые решения.** Таблица D01–D27: точка → решение (конкретно, 1–3 предложения) → согласие (единогласно / большинство / спор) → кто был против и почему (1 строка) → ссылки на обоснование.
3. **Подробности по спорным точкам.** Для каждой точки со статусом «спор» и для каждой, где меньшинство изменило решение: аргументы сторон и почему выбран этот вариант.
4. **Сводная спецификация проверок.** Таблица по ВСЕМ ID каталога: фаза и источник данных → суть детекта (1–2 предложения) → уровень по умолчанию → когда уровень понижается или находка становится inconclusive → crmCode (как в каталоге; ошибки каталога пометь) → правовой якорь (кратко) → этап плана.
5. **Ключевые контракты.** Модель результата (статусы, severity, confidence), семантика `--fail-on` и кодов 0/1/2 со всеми пограничными случаями, поля находки и evidence, правила fingerprint и suppression, правило «нераспознанный баннер → info». Только то, о чём договорились, без кода.
6. **Ошибки, найденные в ходе консенсуса.** Таблица: где (предложение, ресёрч, каталог, ТЗ) → в чём ошибка → исправление → кто нашёл.
7. **Непроверенные факты.** Таблица: утверждение → почему важно → как проверить → до какого этапа.
8. **Вопросы заказчику.** Нумерованный список, по важности.
9. **Риски.** Топ-12 из всех раундов: вероятность, влияние, мера, владелец (заказчик или разработка).
10. **ADR-кандидаты.** Список с выбранным вариантом, по одной строке.

Пиши плотно, без воды. Каждое решение — конкретное: значения, флаги, имена, а не «надо подумать». Запиши файл инструментом Write. Других файлов не трогай.
