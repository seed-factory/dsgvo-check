## 1. Позиционирование и границы

**`dsgvo-check` — Apache-2.0 CLI для воспроизводимого наблюдения за privacy и security признаками немецких сайтов и проверки этих наблюдений по настраиваемой политике CI.**

Основа проекта — [ТЗ](/Users/user/Documents/germany/coding-memes/specs/dsgvo-check_TZ.md), приоритеты и идентификаторы — [каталог](/Users/user/Documents/germany/coding-memes/specs/dsgvo-check_katalog-proverok.md). TypeScript + Playwright и Apache-2.0 считаю зафиксированными.

**Релизный MVP:**

- Все **15 P0**, включая PRIV-01/02 и семь CMP для CONSENT-04.
- Независимые сценарии до выбора, после отказа и после принятия.
- Ограниченный обход публичных страниц.
- JSON со стабильной схемой, консоль, самостоятельный HTML и экспорт PDF.
- Коды `0/1/2`, GitHub Action, GitLab-шаблон, Docker и npm.
- Для каждого реализованного ID — нарушающая и чистая фикстуры.
- Документация методики, покрытия и ограничений.

HTML/PDF включаю в предлагаемый объём проекта, хотя ТЗ требует только JSON и консоль. Их стоимость отдельно учтена в плане.

**Сознательно вне MVP:** полный юридический аудит, DSGVO-Zertifizierung, авторизованные разделы, отправка форм, покупки, CAPTCHA bypass, эксплуатация CVE, полный crawl, batch-платформа, история аудитов, Firefox/WebKit, автоматическая оценка договоров и Drittlandtransfer, server-to-server tracking, оценка допустимости Pur-Abo, PDF/A, BFSG и Lighthouse.

## 2. Архитектура

**Поток данных:**

> План скана → сбор наблюдений → минимизация данных → неизменяемый снимок → чистые проверки → применение ruleset → связывание находок → baseline → решение CI → репортеры.

Один публикуемый npm-пакет, внутри — независимые слои. Приватные пакеты для фикстур и тестовых инструментов допустимы; публичное монорепо из множества пакетов на старте не нужно.

| Модуль | Ответственность |
|---|---|
| `cli/config` | Аргументы, конфигурация, проверка URL, выбранные проверки, бюджет и выходные форматы. |
| `planner` | Scope, страницы, сценарии, зависимости проверок и необходимые возможности сборщиков. |
| `runner` | Исполнение плана, deadlines, отмена, изоляция ошибок, статусы покрытия. |
| `collectors/browser` | Сеть, frames, DOM-факты, CMP, cookies/storage, последовательность действий. |
| `collectors/http` | Ограниченные HTTP-пробы, redirect chains, заголовки, получение документов. |
| `collectors/tls` | Сертификат и диагностические TLS-соединения. |
| `collectors/dns` | DNS-ответы, ошибки резолвера, почтовые записи. |
| `policy-document` | Извлечение, нормализация и структурирование Datenschutzerklärung/Impressum. |
| `classification` | Сервис, назначение, first/third party, сигнатура и уверенность. |
| `checks` | Детерминированное сопоставление снимка с условиями конкретного ID. |
| `assessment` | Уровни, применимость, немецкие/английские шаблоны, ссылки на правовые материалы. |
| `correlation/gate` | Связи между находками, fingerprint, suppression, решение по порогу. |
| `reporters` | JSON, консоль, HTML, PDF из одного итогового отчёта. |
| `data/update` | Валидация, установка и фиксация версий справочников; отдельно от скана сайта. |

Короткий контракт проверки:

```ts
interface Check {
  id: CheckId;
  version: string;
  priority: "P0" | "P1" | "P2";
  requires: readonly Capability[];
  evaluate(
    snapshot: Readonly<ScanSnapshot>,
    context: Readonly<EvaluationContext>
  ): CheckResult;
}

interface CheckResult {
  status: "completed" | "partial" | "inconclusive" | "error" | "skipped";
  candidates: readonly FindingCandidate[];
  limitations: readonly Limitation[];
}
```

`EvaluationContext` содержит фиксированное время оценки, конфигурацию и версии данных. Проверка не получает Playwright Page, HTTP-клиент, произвольный доступ к сети или глобальные часы.

**Расширение:** новая папка проверки содержит модуль, декларацию возможностей, сообщения и фикстуры. На сборке из деклараций генерируется manifest. Ядро не перечисляет ID вручную. Новый сборщик подключается через отдельный контракт capabilities, если существующих артефактов действительно недостаточно.

Runtime-загрузка произвольного кода из npm или конфигурации сайта в MVP отсутствует. Будущие плагины — только явно установленные пользователем доверенные модули.

**Данные:**

- `data/services/`: продукты, домены, URL/payload-сигнатуры, операторы, aliases, категории, происхождение записи.
- `data/cmp/`: версии и признаки CMP, первый слой, действия, чтение состояния.
- `data/rulesets/`: уровни, подтипы, пороги, применимость, версии алгоритмов.
- `data/messages/{de,en}/`: фактические тексты и рекомендации.
- `data/legal/`: статические комментарии, источники, `verifiedAt`, `reviewBy`.
- `data/vulnerabilities/`: отдельные индексы источников и manifest лицензий.

Обновление данных меняет `rulesetVersion`/`datasetVersion`, даже если код CLI не изменился. Скан использует один зафиксированный набор данных от начала до конца.

## 3. Жизненный цикл скана и фазы согласия

### Контексты и сценарии

Выбираю **полный Chromium в new headless**, поставляемый вместе с закреплённой версией Playwright. Для каждого независимого сценария — свежий временный persistent-профиль в ограниченном временном каталоге. Пользовательский профиль Chrome не используется.

Это решение учитывает эксперимент первого раунда о различии preconnect в persistent и incognito-подобных контекстах. **⚠ проверить воспроизводимость этого различия на выбранной поставке Chromium.** Сам эксперимент не доказывает полноту наблюдения preconnect.

| Сценарий | Контекст | Действия |
|---|---|---|
| **A: до выбора** | Свежий desktop-профиль | Открыть выбранные страницы без действий с CMP. На каждой странице сначала спокойное наблюдение, затем отдельно помеченный ограниченный scroll для lazy loading. |
| **B: отказ** | Другой свежий desktop-профиль | Открыть стартовую, снять первый слой, выполнить однозначный отказ через UI, проверить состояние, reload, посетить выбранные контрольные страницы. |
| **C: принятие** | Третий свежий desktop-профиль | Принять через UI, посетить контрольные страницы для инвентаризации сервисов и PRIV-01/02. |
| **M: мобильный первый слой** | Свежий профиль с мобильным viewport | Стартовая страница: распознавание CMP, доступность первого слоя и отказа. Мобильный обход всего сайта в MVP не заявляется. |

A и A′ не требуют двух независимых профилей: A′ — подфаза наблюдения после нейтрального действия. Между A, B и C состояние не переносится. Внутри B/C оно сохраняется естественно, включая cookies, storage и reload.

Каждый запрос маркируется по **времени начала** относительно действия. Ответ на запрос, начатый до отказа, не становится запросом «после отказа».

Отзыв ранее принятого согласия — самостоятельный будущий сценарий, не эквивалент B.

### Выбор страниц и scope

По умолчанию **шесть уникальных контентных URL**, включая документы:

1. Стартовый URL.
2. Datenschutzerklärung.
3. Impressum.
4. Kontakt/Anfahrt/Standort.
5. Страница с вероятным embed: Über uns/Geschichte/Referenzen.
6. Ещё один отличающийся шаблон: новости, услуги, карьера и т. п.

Сначала используем реальные ссылки. Sitemap — ограниченный fallback, без массовой загрузки индексов. Дополнения Datenschutzerklärung обрабатываются отдельным документным бюджетом: максимум три связанных документа.

В A посещаем все выбранные URL; в B/C — стартовую, Kontakt и одну страницу с наиболее вероятными embeds. Не обещаем post-consent покрытие остальных страниц.

Автоматический scope — конечный origin плюс явно обнаруженный переход apex↔www в пределах одного регистрируемого домена. Другие поддомены требуют allowlist; сам факт одинакового eTLD+1 не разрешает их обход. Внешние legal-документы допускаются адресно, без crawl их сайта.

Redirect на другой регистрируемый домен фиксируется и останавливает автоматическое расширение scope. SPA-маршруты учитываются как отдельные URL, если доступны через разрешённую навигацию.

LEGAL-01 формулируется исключительно как **«на N из M проверенных страниц»**.

### Ожидание и бюджеты

Стартовые значения для калибровки:

| Ограничение | Значение |
|---|---:|
| Навигация | До 30 секунд |
| Наблюдение A | Минимум 6 секунд, максимум 20 секунд |
| Окно тишины | 2 секунды без новых обычных запросов и без незавершённых коротких запросов |
| Нейтральный scroll | Дополнительно 3–8 секунд на выбранных страницах |
| Наблюдение после действия B/C | Минимум 4, максимум 12 секунд |
| Общий сбор | 8 минут |
| Завершение/запись отчётов | Отдельный резерв 30 секунд |
| PDF | Отдельный deadline до 30 секунд |

WebSocket, EventSource и длинные media-потоки не мешают достижению тишины, но продолжают регистрироваться. `networkidle` не используем как критерий полноты.

Достижение локального лимита наблюдения само по себе не является падением: сохраняются длительность и `quietNotReached`. Исчерпание общего deadline до завершения обязательного плана — операционная ошибка.

Обещание первого раунда «2,5–4 минуты» считаю недостаточно обоснованным, особенно с мобильным сценарием. Ожидание для обычного сайта — несколько минут; **⚠ проверить p50/p95 на калибровочном корпусе**.

### Нагрузка, UA, гео

- Навигации последовательные; между ними минимум 1,5 секунды.
- Дополнительные HTTP-пробы: максимум 2 запроса/с на origin, concurrency 2.
- DNS: concurrency 4, кэш в пределах скана, ограничение глубины и общего числа запросов.
- Browser-generated запросы не обещаем уложить в 2 запроса/с: такое ограничение изменит загрузку сайта. Считаем их отдельно, ограничиваем общий объём и прекращаем чрезмерный прогон.
- Начальные бюджеты: 2 000 браузерных запросов, 50 дополнительных HTTP-проб, 100 DNS-запросов; исключения и достижения лимитов видны в отчёте.
- Соблюдаем `Retry-After`; повторные 429/503 прекращают обход. Автоматический retry браузерного сценария не включается.
- `robots.txt` учитывается для дополнительных страниц; явно заданный стартовый URL проверяется. Пропуски перечисляются.

**UA обязателен и для браузера, и для HTTP-проб:** идентификатор `dsgvo-check/<version>` и реальная ссылка на репозиторий. Версию Chromium в browser UA не выдумываем. Ссылку нельзя удалить ради обхода bot detection: это прямое ограничение ТЗ.

`de-DE`, `Europe/Berlin` и viewport фиксируем, но они не задают регион IP. Для воспроизводимого немецкого аудита рекомендуем контролируемый DE-egress; принимаем пользовательский proxy и фиксируем его применение без credentials.

Страну выхода записываем с происхождением: конфигурация оператора, собственный runner либо явно подключённая проверка. Не делаем скрытый запрос к стороннему «what is my IP».

Bot/out-of-region сигналы CMP, challenge и автоматическое согласие без клика сохраняются как ограничения. Подтверждённый bot-specific режим делает зависимые выводы о человеческом consent-поведении `inconclusive`; сами сетевые факты остаются в снимке.

## 4. Баннеры и CMP

Собственные адаптеры — в порядке каталога. Данные первого раунда служат начальной картой, а не гарантией совместимости с любой версией.

| CMP | Начальные признаки | Что должен знать адаптер |
|---|---|---|
| **Borlabs** | `BorlabsCookie`, `BorlabsCookieBox`, семейство `_brlbs`/`brlbs-*` | Различать v2/v3, первый слой и настройки, essential-only, consent-cookie, отложенное появление и bot mode. |
| **Cookiebot** | `Cookiebot`, `CybotCookiebotDialog`, loader Cookiebot | Decline первого слоя, категории consent, `hasResponse`, out-of-region/spider сигналы. |
| **Complianz** | `cmplz-*`, объект `complianz`, consent-cookie | Варианты opt-in/opt-out, регион, категории и сохранение отказа. |
| **Usercentrics** | `UC_UI`/`__ucCmp`, `usercentrics-*` | Версии UI, open shadow DOM, accessible names, состояние категорий. |
| **CCM19** | `ccm-widget`, loader `app.js`, `ccm-*` | Первый слой и control panel; cookie/localStorage. **⚠ проверить API и поддерживаемые версии.** |
| **Real Cookie Banner** | `consentApi`, характерная структура dialog | Не опираться на случайные ID; структурные признаки, чтение состояния, bot-specific acceptance. |
| **CookieHub** | `cookiehub`, `.ch2-*` | Не путать переход в настройки с отказом первого уровня; проверять категории и answered-state. |

**Уверенность распознавания:**

- Для действия нужен score ≥0,90, минимум два независимых признака и один однозначный видимый элемент.
- При конфликте адаптеров, неизвестной версии или нескольких подходящих действиях — без клика.
- Число 0,90 — инженерный порог правил, не статистическая вероятность.
- `eval`, force-click, программное `denyAll()/acceptAll()`, косметическое скрытие баннера и изменение closed shadow DOM в доказательном прогоне запрещены.

Обобщённая эвристика ищет видимый dialog/overlay, cookie/consent-лексику, группы actionable элементов и признаки первого слоя во всех доступных frames и open shadow roots. Она обнаруживает **кандидата**, но не получает право объявить CONSENT-04.

**Не распознал → `info: „Banner nicht erkannt“`.** Состояние зависимых проверок — `inconclusive`, а не «отказ отсутствует».

`@duckduckgo/autoconsent` можно использовать как закреплённый резервный детектор и источник отдельных правил с соблюдением [MPL-2.0](https://github.com/duckduckgo/autoconsent/blob/main/LICENSE). Автоматический opt-out движка не используем как доказательство первого уровня: он может пройти настройки, вызвать API или скрыть UI.

**Проверка отказа состоит из независимых результатов:**

1. Действие реально выполнено через доступный UI.
2. CMP сообщает отказ от необязательных категорий либо это подтверждает известный формат consent-state.
3. Отказ сохраняется после reload.
4. Отдельно наблюдаем, какие запросы и storage-события происходят дальше.

Отсутствие трекеров не является обязательным условием признания **состояния отказа**: иначе невозможно обнаружить CONSENT-05 «CMP сохранил отказ, аналитика продолжается».

Для CONSENT-04 учитываем блокировку контента и наличие принятия на первом уровне. Неблокирующий баннер, отсутствие принятия на первом уровне и Pur-Abo требуют отдельной интерпретации. Геометрия кнопок — evidence, не самостоятельный юридический алгоритм. Это соответствует нюансам Rn. 124–127 [DSK OH Digitale Dienste](https://www.datenschutzkonferenz-online.de/media/oh/OH_Digitale_Dienste.pdf).

## 5. Модель данных и контракт

Разделяем три сущности:

- **Observation:** что непосредственно наблюдали.
- **CheckResult:** что удалось проверить и с какими ограничениями.
- **Finding:** какой технический признак выделил версионированный ruleset.

`critical` означает высокий приоритет по политике инструмента, не доказанное нарушение закона.

        "disposition": { "enum": ["active", "suppressed"] }
      }
    },
    "evidence": {
      "type": "object",
      "required": ["id", "type", "source", "observedAt", "data"],
      "properties": {
        "id": { "type": "string" },
        "type": {
          "enum": [
            "url", "request", "cookie", "header", "dns",
            "tls", "dom", "document", "storage", "consent", "metric"
          ]
        },
        "source": { "type": "string" },
        "observedAt": { "type": "string", "format": "date-time" },
        "data": { "type": "object" }
      }
    }
  }
}

### Версионирование и CRM

`schemaVersion` — отдельный SemVer, начально `1.0.0`. Новые необязательные поля — minor; изменение обязательных полей, типов или смысла — major. Добавление нового варианта закрытого evidence union также требует явной политики совместимости; нельзя обещать одновременно строгий enum и произвольное расширение без последствий.

`crmCode` — независимый адаптер, не источник severity:

- Сохраняем точные значения P0/P1 из каталога.
- У VULN выбираем один из двух кодов по итоговой классификации.
- EMBED-03 до решения заказчика сохраняет странный, но заданный `T1_MAPS_BEFORE_CONSENT`.
- Для P2 — обязательное поле с `null`, пока код не определён.
- `T0` не становится четвёртым severity и не превращается в выдуманный CRM-код.

### Fingerprint и baseline

`fingerprintVersion=1`; SHA-256 канонического стабильного ключа:

> checkId + subtype + нормализованный scope + субъект.

Субъект зависит от проверки: сервис и вид события; cookie name/domain/path/partition; имя заголовка и маршрут; mail-domain; component/package + advisory ID; маршрут и тип legal-документа.

Timestamp, локализованный текст, cookie values и случайные query-параметры не входят. Семантически значимые пути и параметры сохраняются в ключе согласно правилам конкретного ID.

Baseline содержит fingerprint, причину, владельца, срок и максимальный согласованный уровень. Повышение severity или существенное изменение семантики правила требует нового подтверждения suppression. Подавленные findings остаются в отчёте. Ошибки исполнения baseline не подавляет.

### Точная семантика `--fail-on` и кодов

По умолчанию `--fail-on critical`.

- `critical`: код `1`, если есть хотя бы одна активная `critical`.
- `warning`: код `1`, если есть хотя бы одна активная `warning` или `critical`.
- `info` никогда не достигает этих порогов.
- Сравнение включительное: «достигает порога», а не строго «выше».
- `--no-fail-on` отключает только возврат `1`.
- После назначения severity нет скрытого фильтра по confidence. Неуверенные кандидаты получают `info` либо `inconclusive`, а не молча исключаются из гейта.

**Предлагаемый приоритет: `2 > 1 > 0`.**

| Ситуация | Результат |
|---|---|
| Скан завершён, порог не достигнут | `0`. |
| Порог достигнут | `1`. |
| Исключение в любой включённой проверке, включая P1/P2 | Частичный отчёт, проверка `error`, код `2`. Остальные проверки продолжаются, если возможно. |
| Стартовый сайт недоступен, WAF/CAPTCHA не позволяют получить сайт | `scan.failed`, код `2`; это не privacy finding. |
| Общий timeout или обязательный сборщик потерян | Частичный JSON и код `2`. |
| DNS timeout/SERVFAIL делает обязательную MAIL-проверку невыполнимой после ограниченного retry | Неполный обязательный сбор, код `2`; не «запись отсутствует». |
| Баннер не распознан | `info „Banner nicht erkannt“`; зависимые проверки `inconclusive`; сам по себе код `0`. Другие findings могут дать `1`. |
| Известный баннер не содержит доступного отказа | Результат CONSENT-04 по ruleset; это finding, а не ошибка выполнения. |
| Достигнут локальный hard cap ожидания тишины, данные собраны | Ограничение окна наблюдения; код по findings, не автоматически `2`. |
| Навигация timeout, но достаточный документ получен | `partial`, оценка доступных данных. Если обязательные данные получить нельзя — `2`. |
| Политика действительно отсутствует/ссылка сломана | LEGAL-01; PRIV-01/02 `skipped` по зависимости. Это не авария сканера. |
| Часть crawl ограничена robots/scope, стартовая и обязательный план выполнены | Явное ограничение покрытия; код по findings. |
| Ошибка сохранения JSON или запрошенного HTML/PDF | `2`; уже созданные результаты сохраняются. |
| Одновременно critical и ошибка выполнения | `2`, critical остаётся в отчёте. |

Это **явное уточнение ТЗ**: код `2` означает невозможность корректно выполнить заказанную операцию, включая внешние причины. Буквальное «сканер сам упал» не покрывает недоступную цель. Уточнение нужно согласовать, а не скрывать в реализации.

Опциональный `--require-complete` превращает определённые ограничения покрытия в операционный отказ `2`. Он не меняет `info` неизвестного CMP на ложный CONSENT-04.

Статус DPF не выводится из доменного имени. Автоматический live lookup DPF и полный список adequacy decisions в MVP не нужны. **⚠ проверить актуальный правовой статус и охват конкретных организаций перед добавлением таких сведений в отчёт.**

## 8. Отчёты

**JSON — первичный результат.** Консоль, HTML и PDF строятся из него. Повторный рендер не обращается к сканируемому сайту.

- **Консоль:** target, среда, покрытие, уровни, незавершённые проверки, решение гейта и путь к JSON. Без оценок «DSGVO bestanden».
- **HTML:** один статичный файл, встроенные CSS и необходимые изображения, без JavaScript, CDN, внешних шрифтов и автоматических сетевых обращений.
- **PDF:** печать собственного HTML через отдельный Chromium-контекст с запрещённой сетью. A4, повторяемые заголовки таблиц, переносы длинных URL, отсутствие обрезанных evidence.
- **JSON stdout:** через явный режим; диагностические логи идут в stderr. По умолчанию — консоль и локальный JSON-файл.
- **Язык:** немецкий по умолчанию, `--lang en`; JSON-идентификаторы и параметры от языка не зависят.
- Немецкие тексты и дисклеймер предоставляет и вычитывает заказчик. Английский текст должен сохранять те же ограничения смысла.

Черновик дисклеймера:

> Dieser Bericht dokumentiert technische Beobachtungen unter den angegebenen Prüfbedingungen. Er ersetzt keine rechtliche Prüfung und bestätigt keine DSGVO-, TDDDG- oder DDG-Konformität. Nicht erkannte Auffälligkeiten und nicht prüfbare Bereiche sind keine Bestätigung ihrer Abwesenheit.

Это текст для вычитки, не готовое юридическое заключение.

**Редактирование до записи на диск:**

- Удаляем cookie values, Authorization, session/access tokens.
- У query и потенциально чувствительных path-сегментов сохраняем только необходимые признаки.
- Произвольные POST bodies и WebSocket payload не экспортируем.
- Из consent-state сохраняем allowlist категорий и состояний, без consent IDs.
- DNS TXT с адресами и документные цитаты минимизируем.
- Скриншоты баннера — опциональные, ограниченная область; в публичные CI artifacts по умолчанию не публикуются.
- HAR, trace и NetLog выключены по умолчанию.

Для корреляции значений внутри запуска при необходимости — временный HMAC с непубликуемым ключом. Обычный SHA-256 cookie не считаем обезличиванием.

Отчёт получает SHA-256; manifest связывает его с минимизированным снимком, конфигурацией и datasets. Подпись может подтвердить целостность и происхождение артефакта, но не истинность юридического вывода.

## 9. Тестирование

Для **каждого реализованного ID** manifest требует:

- `violation` — ожидаемый технический признак и evidence.
- `clean` — отсутствие именно этого признака, а не «юридически чистый сайт».
- Для применимых ID дополнительно `unknown`, `partial/error` и существенные контрпримеры.

У P0 проверяем не только число findings, но ID, subtype, severity, evidence, coverage и отсутствие соседнего ложного finding.

| Уровень | Что проверяем |
|---|---|
| Статика и контракты | Типы, schemas, реестр всех 33 ID с release status, наличие пар фикстур для включённых ID, de/en parity, CRM mapping, лицензии, README. |
| Unit на снимках | Проверки, классификация, версии, aliases/отрицания, fingerprint, baseline, gate и ошибки зависимостей. |
| Интеграция сборщиков | Реальные HTTP/TLS/DNS и Chromium на локальных синтетических сайтах. |
| CLI/поставка | Установка npm, Docker, коды `0/1/2`, Action и GitLab-шаблон, HTML/PDF. |
| Живые канарейки | 10 сайтов заказчика с ручной разметкой и установленным scope, отдельно от PR-гейта. |

**Без интернета:**

- Закрытая контейнерная сеть без внешнего egress.
- Домены `site.test`, `tracker.test`, `cmp.test`, `fonts.test` направляются на локальные endpoints единой картой для браузера, HTTP-клиента и TLS.
- Настоящие TLS-соединения с тестовым CA, SNI, валидным/просроченным/чужим сертификатом.
- Отдельный локальный legacy-TLS endpoint и self-test клиента.
- Локальный DNS-сервер: TXT/MX/CNAME/CAA, chunks TXT, NXDOMAIN/NODATA/SERVFAIL/timeouts.
- Для DNSSEC — подписанная, unsigned и повреждённая зона с настоящим валидатором.
- Незаявленный запрос за границы карты проваливает тест.
- `route.fulfill()` допустим в узких тестах, но не заменяет сетевые интеграционные проверки.

Обязательные браузерные фикстуры: ранний `<head>` request, iframe/open shadow, неизвестный CMP, перекрытая кнопка, refusal-only через второй слой, автоматическое принятие без клика, transient cookie, отвергнутый Set-Cookie, service worker, pagehide beacon, mixed-content upgrade/block и lazy loading.

Для семи CMP — собственные минимальные симуляторы контрактов и отдельные проверки настоящих лицензированных установок. Симуляторы не доказывают совместимость с реальными версиями CMP. Чужой проприетарный код не коммитим ради фикстуры.

**Канарейка:** 10 реальных сайтов к этапу 3; до этого — свои стенды и лицензированные CMP. Ожидания задаются как `mustFind/mustNotFind/allowedInconclusive`, с ручной сверкой тех же фаз и региона. Ночное расхождение создаёт сигнал для разбора, не «исправляет» baseline автоматически.

**Антифлейк:**

- Закреплённые browser/dataset versions, фиксированное время unit-тестов.
- Серверные события и явные conditions вместо случайных sleeps.
- Новые профили; отсутствие параллельной нагрузки на один target.
- Один диагностический retry инфраструктурного сбоя с сохранением первой ошибки.
- Успешный повтор не стирает ранее подтверждённое observation.
- Стабильная сортировка результатов; время и случайные IDs исключены из golden-сравнения.

Критерий релиза: все P0 fixture pairs проходят; на утверждённом корпусе нет известных ложных `critical`, неизвестный CMP всегда даёт требуемое info. Цель precision для будущего расширенного размеченного корпуса — ≥99% для гейтящих critical; **десять сайтов недостаточны, чтобы статистически доказать эту цифру**.

## 10. CI и дистрибуция

**GitHub Action:** composite wrapper над закреплённым Docker image digest. Это позволяет контролировать пользователя, mounts, seccomp и лимиты. GitHub прямо документирует root-поведение Docker actions, поэтому его простоту здесь не выбираю: [Dockerfile support](https://docs.github.com/en/actions/reference/workflows-and-actions/dockerfile-support).

Action:

- Передаёт inputs как аргументы/переменные без shell interpolation пользовательского текста.
- Не монтирует весь workspace; только конфигурацию read-only и отдельный output-каталог.
- Не передаёт secrets и служебные токены.
- Выдаёт `exit-code`, summary и пути отчётов.
- Сохраняет исходный код сканера после формирования outputs.
- Публикация artifacts — отдельный шаг `always()`, с явным сроком и доступом.

**GitLab:** обычный версионированный include-шаблон обязателен; Catalog component — последующее удобство. `allow_failure: false`, `artifacts: when: always`, закреплённый image digest. Для self-managed предоставляется локальное копирование шаблона; `include:remote` и integrity используются при поддержке инстансом. Основа — [GitLab YAML reference](https://docs.gitlab.com/ci/yaml/#includeremote).

**Docker:** Linux amd64 как обязательная стартовая платформа; arm64 — только после нативных smoke/security tests. Node 24 как консервативный runtime, полный закреплённый Chromium, non-root, sandbox, init, шрифты, отдельные tmpfs и output. Не полагаемся на размер образа из оценок первого раунда.

Node 24/26 проверяем в CI, минимальный runtime — 24. Поддержку Node 22 не добавляем ради расширения матрицы: он близок к EOL по [официальному графику Node](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json).

**npm:** один CLI-пакет. После обычной установки `dsgvo-check https://example.de` не требует конфига. Chromium нужной revision готовится при первом запуске с прозрачным сообщением либо заранее командой подготовки. Root/apt-операции автоматически не выполняются; системные prerequisites Linux документированы. Docker предоставляет готовую среду одной командой.

Официально тестируем Linux и macOS npm-режим; Windows до отдельной проверки — best effort. Системный плавающий Chrome не является эталонным движком.

**Пример репозитория:** отдельный example с управляемым fixture-сайтом:

- «bad» отправляет собственный синтетический tracking-event до выбора → Action возвращает `1`.
- «clean» → `0`.
- Сломанный запуск/недоступная цель → `2`.
- Отчёты сохраняются во всех трёх случаях.
- Внутренняя тестовая сеть разрешается адресно, без глобального доступа к private ranges.

**Релизы:**

- Один commit связывает npm, image, Action и GitLab-шаблон.
- SemVer CLI; независимые schema и ruleset versions.
- Lockfile, dependency/license audit, SBOM, changelog.
- npm trusted publishing через OIDC и provenance по [документации npm](https://docs.npmjs.com/trusted-publishers/).
- OCI image подписан keyless Sigstore/cosign, с attestations и SBOM.
- Перед публикацией — установка собранного npm tarball и smoke готового image.
- Версионные artifacts не перезаписываются; security rebuild получает новую версию.
- Actions закрепляются по SHA, images — по digest.

## 11. Безопасность и этика самого сканера

**Граница пассивности:** обычная загрузка публичного сайта, необходимые CMP-действия и ограниченные документированные технические запросы. В строгом сетевом смысле сканер активен; продуктовый смысл — без эксплуатации, разрушительных действий и обхода доступа.

Запрещены перебор credentials/backup-имён, инъекции, exploit headers, login attempts, XML-RPC method calls для атаки, CAPTCHA bypass, использование найденных секретов и реконструкция Git.

FILE/ADMIN — отдельный opt-in профиль для разрешённой области. Флаг пользователя не создаёт разрешения владельца сайта.

**FILE-01:** не более десяти фиксированных путей, максимум 4 KiB декомпрессированных данных на ответ, жёсткий stream abort даже при игнорировании Range. Тело не сохраняется; секреты не печатаются, не хешируются для публичного отчёта и не используются. После достаточного сигнала исследование конкретной экспозиции прекращается.

**Изоляция:**

- Недоверенный JS запускается в отдельном browser-процессе/контейнере на одноразовом runner без secrets и чувствительных mounts.
- Chromium sandbox включён. Автоматический fallback на `--no-sandbox` отвергаю.
- Non-root, cap-drop, no-new-privileges, проверенный seccomp, лимиты CPU/memory/pids/tmpfs.
- Сам Playwright предупреждает, что стандартный образ не предназначен как готовая защита для недоверенных сайтов; собственная упаковка не снимает необходимость изоляции: [Playwright Docker](https://playwright.dev/docs/docker).

**SSRF и сеть:**

- HTTP(S) URL без userinfo; redirects повторно проверяются.
- По умолчанию запрещены loopback, private, link-local, metadata и специальные IPv4/IPv6 диапазоны.
- DNS-проверки не ограничиваются исходным URL: адрес проверяется на фактическом соединении, с защитой от rebinding.
- Для браузера нужен контролируемый egress broker/CONNECT proxy с закреплением разрешённого upstream IP; без TLS MITM.
- В официальном CI-профиле сеть запрещает обход broker прямыми соединениями, UDP/QUIC/WebRTC.
- В npm-режиме без сетевой изоляции нельзя обещать ту же границу защиты от компрометации браузера; это явно отражается в среде отчёта.
- Внутренние сайты — отдельная адресная allowlist и изолированный runner.

Не используем `context.route()` как основной механизм security-наблюдения: Playwright подтверждает, что routing [отключает HTTP-кэш](https://playwright.dev/docs/api/class-browsercontext#browser-context-route). Он также не является полной сетевой границей.

**XSS и отчёты:** все строки экранируются по контексту; чужой HTML не вставляется. Только разрешённые URL-схемы, статичный HTML с CSP, никаких активных SVG/скриптов из target. Терминал очищается от ANSI, bidi и workflow-команд.

Нет телеметрии и скрытого облачного анализа. Публичный рейтинг «нарушителей», Abmahnung generator и автоматическая отправка претензий отсутствуют. Apache-2.0 не используется как фиктивный запрет нежелательного применения.

## 14. Решения за заказчиком

Ниже — вопросы, где инженерного решения недостаточно. Они не требуют остановить проектирование, но должны быть закрыты до фиксации production-ruleset.

| Вопрос | Варианты | Рекомендация |
|---|---|---|
| Что означает `critical`? | Юридически доказанное нарушение / технический факт, запрещённый политикой / потенциальный риск | **Технический факт по утверждённой политике.** Не обещать юридическую доказанность. |
| Какие pre-consent операции допускают гейт? | Все сторонние запросы / перечень целей и операций / только cookies | **Контекстный перечень целей и операций**, unknown отдельно. |
| Advanced Consent Mode и cookieless pings | Всегда допустимы / всегда critical / отдельная оценка | **warning с конкретным evidence**, повышение только по утверждённым условиям. |
| CONSENT-04 | Слово Ablehnen / работоспособная доступная альтернатива / одинаковый дизайн | **Работоспособная альтернатива**, с отдельными примерами blocking/nonblocking, mobile и Pur-Abo. |
| Достаточность Datenschutzerklärung | Каждый бренд обязателен / оператор или релевантная категория / любое упоминание | **Оператор/продукт/релевантное описание**, достаточность остаётся экспертной. |
| MAIL и технические headers | Любое отклонение critical / hardening warnings / только inventory | **Hardening warnings/info**; `~all` и отсутствие DKIM по словарю не приравнивать к отсутствию защиты. |
| FILE/ADMIN | На любых публичных сайтах / только при разрешении / исключить | **Отдельный разрешённый профиль**, P2, короткий фиксированный план. |
| Данные аудита | Полные HAR/скриншоты / минимизация / только агрегаты | **Минимизированные evidence**, чувствительные материалы отдельно; утвердить доступ и сроки хранения. |
| Drittlandtransfer | По IP / по владельцу бренда / технические сигналы и ручное установление цепочки | **Последний вариант**; страна и DPF не определяют автоматически законность. |
| Правовые обновления | Автоизменение с сайта регулятора / экспертно вычитанные data releases / редкие релизы CLI | **Экспертно вычитанные data releases** с источниками и датами. |
| Коммерческое использование и тексты | Только OSS / платные технические отчёты / юридические заключения | До продаж определить с юристом **RDG, ответственность и лицензию текстов**, не считать дисклеймер универсальным решением. |

Три дополнительных контрактных решения, которые не требуют DSGVO-экспертизы, но требуют владельца продукта:

1. Принять расширенную семантику кода `2` для невозможного обязательного скана.
2. Утвердить CRM mapping для P2 и EMBED-03; до этого сохранять текущие значения/null.
3. Подтвердить включение HTML/PDF в предлагаемый MVP и его оценку.

**Правовые материалы первого раунда требуют более строгой маркировки.** Переговорный мандат Совета по Digital Omnibus подтверждён первичным документом **ST 14756/26 от 22.10.2026**; это мандат для переговоров, а не действующее освобождение аналитики от согласия. Preview-профиль в MVP не нужен. [Документ Совета](https://data.consilium.europa.eu/doc/document/ST-14756-2026-INIT/en/pdf).

**⚠ проверить перед юридической вычиткой:** текущий статус апелляции DPF, актуальные признанные Einwilligungsverwaltungsdienste, спорные судебные ссылки и применимость CRA к модели сопровождения проекта. Их нельзя переносить из сводки как проверенные production-факты.

Также не принимаю три чрезмерно сильных вывода первого раунда:

- Отсутствие DKIM по «известным» selectors даже при известном MX не доказывает, что DKIM не настроен.
- Статус сервера нельзя надёжно вывести из любого TLS handshake failure.
- Статические шаблоны и запрет LLM сами по себе не решают вопрос RDG; значение имеют содержание и способ предоставления услуги.

## 15. ADR-кандидаты

1. **Назначение продукта:** технические observations и CI policy, без автоматической юридической квалификации.
2. **Релизный объём:** все 15 P0; HTML/PDF включены в проект; P1/P2 имеют отдельный бюджет.
3. **Архитектура:** collectors → минимизированный immutable snapshot → pure checks → assessment → gate → reporters.
4. **Расширяемость:** декларативный build-time manifest checks/capabilities, без runtime discovery чужого кода.
5. **Браузер:** закреплённый полный Chromium new headless, свежий временный persistent-профиль на независимый сценарий.
6. **Сценарии:** A/B/C и ограниченный mobile M; отказ и его сетевой эффект — независимые результаты.
7. **UA и достоверность:** идентификатор и ссылка обязательны в browser/HTTP UA; bot/geo effects отражаются в coverage.
8. **CMP:** семь собственных адаптеров; unknown → `info „Banner nicht erkannt“`; без API-mutators и force-click.
9. **Область обхода:** шесть контентных URL, явный scope, отдельные документные лимиты, отсутствие обещания полного сайта.
10. **Evidence:** попытка, принятие, передача, ответ и cache/SW различаются; raw values не экспортируются.
11. **JSON:** Schema 2020-12, независимый SemVer и опубликованная политика совместимости.
12. **CI-коды:** включительный severity threshold; операционный приоритет `2 > 1 > 0`; неизвестная CMP отдельно.
13. **Fingerprint/baseline:** версионированный стабильный субъект, причина/владелец/срок, защита от подавления повышенной тяжести.
14. **Данные:** свой каталог плюс разрешённые snapshots; лицензия и происхождение каждой внешней базы сохраняются.
15. **VULN:** WPVulnerability + Retire.js + разрешённые GHSA/OSV + KEV; никакого вывода об эксплуатации конкретного сайта.
16. **Drittlandtransfer:** вспомогательные сведения с provenance; GeoIP выключен по умолчанию и не влияет на severity.
17. **Пассивность:** ограниченные неразрушающие действия; FILE/ADMIN opt-in, без перебора и использования секретов.
18. **Изоляция:** sandbox обязателен, no-sandbox fallback отсутствует; официальный CI-профиль с контролируемым egress.
19. **Отчёты:** первичный JSON, статичный offline HTML, PDF из него в отдельном контексте.
20. **Проверка качества:** fixture pair для каждого реализованного ID, дополнительные unknown/error cases и независимые live canaries.
21. **Поставка:** npm и подписанный digest-pinned OCI image; composite GitHub Action и обычный GitLab include.
22. **Владение ruleset:** технические данные ревьюит разработка, правовые тексты и применимость — заказчик; новые версии не меняют уже начатый скан.
