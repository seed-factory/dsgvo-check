## 2. Ошибки в предложениях

Ниже «ошибка» означает неверное утверждение, внутреннее противоречие или алгоритм с конкретным контрпримером. Отдельно отмечены спорные решения и незакрытые контракты.

### Opus

Источник: [claude-opus-5.5_proposal.md](/Users/user/Documents/germany/coding-memes/docs/consensus/round-2/claude-opus-5.5_proposal.md).

**Ошибки и противоречия**

1. **Отсутствие CMP-скрипта ошибочно исключает геотаргетинг.** §3.8, строка 313: «CMP-скрипта на странице нет вовсе (**гео-таргетинг невозможен**)». Географическое решение может принять сервер/CDN, inline-код или собственная CMP. Удалить это условие повышения CONSENT-03 до critical: отсутствие обнаруженной библиотеки не устанавливает причину отсутствия баннера.

2. **Consent-cookie без клика ошибочно превращена в доказательство бот-режима.** §3.9, строка 317: «общий признак — consent-cookie любой CMP в фазе A без взаимодействия». CMP может сохранять essential/default-state, идентификатор или версию политики до решения. Автоматический `granted` также может быть настоящим дефектом сайта; подавлять consent-находки можно только при дополнительных признаках специальной ветки для ботов.

3. **`areAllConsentsAccepted()` недостаточно для подтверждения отказа.** §4.2, строка 354 предлагает его как состояние Usercentrics v2. Значение `false` совместимо с отсутствием решения и частичным согласием. Для `stateDenied` нужны готовность CMP, факт ответа и состояние всех необязательных категорий, а не отрицание «принято всё».

4. **Critical за событие пересекается с обещанным warning для cookieless pings.** §6.2, строка 592: «хит с идентификатором **или событием** до клика» → critical; §14, К8 — cookieless pings → warning. Google документирует cookieless Analytics-pings при загрузке и событиях, включая случайное число на загрузку страницы. Сначала нужен подтип ping и проверка устойчивого идентификатора; `en=page_view` недостаточно. [Google Analytics: состав pings](https://support.google.com/analytics/answer/9976101?hl=en).

5. **Поздние записи cookies исключаются слишком широко.** §6.3, строка 609: «ответы на запросы, начатые до клика, исключаются». Это корректно для утверждения о **новом запросе после отказа**, но не для `Set-Cookie`, принятого уже после отказа. Нужны отдельные временные события request-start, response и storage-write.

6. **HAR обещан очищенным без механизма очистки.** §8, строка 704: «`content: 'omit'` без значений cookies». Эта настройка управляет content; headers и cookies обрабатываются отдельно. Нужен собственный sanitizer либо отказ от обещания очищенного HAR. [Исходник HAR tracer Playwright](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/har/harTracer.ts).

7. **Google DKIM selector назван фиксированным.** §6.3, строка 613: «документированными фиксированными селекторами (Google `google`…)». Google прямо разрешает другой prefix. MX + отсутствие `google._domainkey` не обосновывают warning о ненастроенном DKIM. [Google Workspace: настройка selector](https://knowledge.workspace.google.com/admin/security/set-up-dkim).

8. **Неверное объяснение отказа от SARIF.** §1.3, строка 38: «Оба формата требуют путь к файлу и номер строки». Для SARIF это неверно: стандарт допускает результаты без такой локации и содержит `webRequest`/`webResponse`. Ограничения конкретного GitHub importer нужно проверять отдельно от возможностей формата. [SARIF 2.1.0, §3.27](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html).

**Спорные решения**

- §5.7: приоритет находки над нефатальной ошибкой и зависимость ошибки от `maxSeverity` усложняют CI-контракт. Это продуктовый выбор, а не техническая необходимость.
- §3.4: невоспроизводимость запроса в более коротком втором окне понижает уверенность прямого наблюдения. Следует понижать утверждение о регулярности поведения, не автоматически достоверность уже записанного запроса.
- §11.3: автоматический fallback без sandbox — риск поставки.
- PDF-политики отложены в P1 при обязательном PRIV-01. Это допустимое ограничение только с явным `inconclusive`; такой релиз не должен называться поддерживающим PDF-политики.
- §4.4: обнаружение цены и `Abo` слишком слабое основание целиком исключать CONSENT-04.

### Fable

Источник: [claude-fable-5.1_proposal.md](/Users/user/Documents/germany/coding-memes/docs/consensus/round-2/claude-fable-5.1_proposal.md).

**Ошибки и противоречия**

1. **CONNECT-прокси не может выполнять заявленное HTTP-регулирование HTTPS-трафика.** §3, строка 178: «лимиты применяются и к браузерному трафику»; §11, строка 512: proxy «применяет token-bucket на хост и считает запросы». Без TLS MITM туннель не раскрывает HTTP-запросы и `Retry-After`; HTTP/2 может передать много запросов через одно соединение. HTTP-события считать в браузере, соединения — на proxy; ресурсы не задерживать. [RFC 9110, CONNECT](https://www.rfc-editor.org/rfc/rfc9110.html#name-connect).

2. **Положительный контроль ошибочно объявлен обязательным доказательством классификации.** §6, CONSENT-05, строка 358: «если в C сервис не грузится, а в B грузится — это ошибка классификации, не находка». Возможны A/B, ротация, ошибка CMP именно в reject-ветке или различие загрузок. Сильный tracking-факт в B сохраняется; отсутствие в C — повод исследовать расхождение.

3. **Неисчезновение UI ошибочно обрывает CONSENT-05.** §4, строка 221: если UI не закрылся, B становится `inconclusive`. CMP может сохранить отказ и оставить панель открытой либо сменить первый слой на сообщение. Определять отказ по состоянию, а UI-transition хранить отдельно; иначе теряется настоящий «отказ сохранён, tracking продолжается».

4. **Рабочие модалки объявляются сломанными ссылками.** §6, LEGAL-01, строка 357: «`#`/пусто/`javascript:` → `link-broken`». Эти значения могут запускать Impressum/Datenschutz в модалке. Проверять действие и содержимое; без проверки — `unresolved`, не broken.

5. **CONSENT-01 допускает critical по попытке запроса.** §6, строка 345 включает `attempted`, а severity назначается категории analytics/ads. Такая попытка могла быть заблокирована до передачи. Имеющееся поле state не исправляет алгоритм, пока delivery-state не участвует в условии уровня.

6. **Географические признаки переинтерпретированы.** §3, строка 186: «Consent Mode `region` без `DE`» — геосигнал; `--require-eu-egress` удовлетворяется proxy либо `--assume-region eu`. Список региональных настроек не сообщает местоположение посетителя; произвольный proxy также не доказывает EU-egress. Google поддерживает несколько региональных defaults, включая более специфичные подразделения. [Региональные правила Google](https://developers.google.com/tag-platform/security/guides/consent#regional_behavior).

7. **Baseline скрывает усиление находки.** §5, строка 284: порог учитывает «только новые fingerprint’ы», а severity в fingerprint не входит. Уже принятая info/warning может стать critical и остаться подавленной. Хранить согласованный максимальный уровень и семантическую версию условия.

8. **Внутреннее противоречие ADMIN-01.** Таблица §6, строка 380: «базовый профиль (3 GET)»; §11, строка 504: ADMIN-01 — opt-in. Это меняет фактический сетевой план, поэтому должно быть устранено до реализации.

9. **Окно отрицания не устанавливает смысл предложения.** §6, PRIV-01, строка 343: любой `ohne`/`nicht` в ±80 символах даёт `named-negated`. «Wir verwenden Google Analytics ohne Cookies» не означает «Google Analytics не используется». Нужна привязка отрицания к предикату и субъекту; неподдерживаемая конструкция — неоднозначность.

**Спорные решения**

- Мобильный viewport отложен, хотя он способен изменить результат обязательного CONSENT-04.
- `--min-confidence high` допускает видимый critical, который не роняет CI. Лучше назначать окончательный уровень до gate.
- Warning за любой неблокирующий баннер без отказа — более строгая продуктовая политика, требующая отдельного обоснования, а не прямое следствие DSK Rn. 124–125.
- Порог политики `<2000` символов как признак неполноты произволен: короткий документ может быть извлечён полностью, длинный — лишь частично.

### Sol

Источник: [codex-gpt-6.1-sol_proposal.md](/Users/user/Documents/germany/coding-memes/docs/consensus/round-2/codex-gpt-6.1-sol_proposal.md).

**Подтверждённой правовой ошибки, сравнимой с географическим выводом Opus, не установил. Основные недостатки — незакрытые технические контракты.**

1. **Не выбран полный требуемый тулчейн.** §10, строки 601–607 выбирает Node и поставку браузера; TypeScript compiler/version policy, пакетный менеджер, test runner, linter и сборщик не определены. Это неполнота ответа на архитектурный промпт, а не дефект выбранных технологий.

2. **Actionability не отделена от исходного первого экрана.** §4, строка 191: для действия нужен «однозначный видимый элемент»; §6, строка 400 опирается на actionability. Обычный `locator.click()` прокручивает элемент, поэтому успешный клик не устанавливает доступность отказа на первоначальном экране. Нужен снимок геометрии и hit-testing **до** действия. [Playwright: `locator.click`](https://playwright.dev/docs/api/class-locator#locator-click).

3. **Обязательная фикстура pagehide ещё не закрывает способ захвата.** §9, строка 569 требует pagehide beacon; §12, строка 667 оставляет pagehide capture на spike. Это корректно обозначенный, но критический незакрытый контракт: пока spike не покажет capture и attribution после разрушения документа, полноту CONSENT-05 обещать нельзя. **⚠ проверить** на закреплённой сборке.

4. **Не описана обработка частично наблюдаемого Consent Mode template API.** §6, строка 437 требует исполняемые default/update, но способ наблюдать GTM template consent API не выбран. Это не эквивалент `dataLayer.push`: Google рекомендует templates использовать `setDefaultConsentState`/`updateConsentState`. Нужна явная capability и fallback, иначе получится `inconclusive` либо пропуск на корректной распространённой интеграции. [Google: consent templates](https://developers.google.com/tag-platform/tag-manager/templates/consent-apis).

**Спорные решения**

- §1, строка 27 оставляет CONSENT-05 вне обязательного MVP, хотя сценарий B уже собирается. Для исходного обещания проекта это недостаточный релизный объём.
- §3, строка 128 ограничивает B/C тремя страницами. Ограничение честно раскрыто, но PRIV-инвентарь будет неполным для интеграций, правильно заблокированных в A на остальных маршрутах.
- §5, строка 368: ошибка любой явно включённой P1/P2 даёт `2`. Я поддерживаю этот контракт, но optional-проверки следует действительно выключать по умолчанию, а не объявлять ошибки нерелевантными задним числом.
- Отказ подтверждённым наблюдениям в автоматическом critical для CONSENT-04/PRIV-02 — консервативная политика, не техническая ошибка.

### Terra

Источник: [codex-gpt-6.1-terra_proposal.md](/Users/user/Documents/germany/coding-memes/docs/consensus/round-2/codex-gpt-6.1-terra_proposal.md).

**Ошибки и незакрытые противоречия**

1. **Docker Action не согласована с обещанной изоляцией.** §10, строка 257 выбирает Docker Action; §11, строка 293 требует non-root и sandbox. GitHub документирует запуск Docker Actions от root и ограничения capabilities. Это не доказательство невозможности любой обёртки со сбросом привилегий, но предложенный способ её не содержит и hardening не обеспечивает. [GitHub: Dockerfile support](https://docs.github.com/en/actions/reference/workflows-and-actions/dockerfile-support).

2. **Не выбран runtime и остальной тулчейн.** §10 описывает npm/Docker без Node baseline, TypeScript toolchain, package manager, runner, linter и сборщика. Следовательно, решение нельзя воспроизводимо подготовить к этапу 1 без дополнительного ADR.

3. **CONSENT-02 теряет краткоживущие JS-cookies.** §6, строка 175: начальное/конечное состояние плюс `Set-Cookie` и доступные storage-записи. Cookie, установленная и удалённая JS между снимками без последующего HTTP-запроса, не попадёт ни в один гарантированно указанный источник. Требуется event-observation JS-записей с отдельными состояниями attempted/accepted/unknown.

4. **CONSENT-03 имеет слишком широкое условие.** §6, строка 176: отсутствие баннера плюс «известные сторонние сервисы». Это включает внешние ресурсы, для которых предложение само не устанавливает consent-зависимую операцию. Нужен явный предикат операции/назначения; известность поставщика не заменяет его.

5. **Не определено, как контракт схемы переживает новые enum.** §5, строка 146: «новые enum-значения обрабатываются как неизвестные». Это правило приложения, но не способ заставить старую строгую JSON Schema принять новое значение. Выбрать открытые строки с реестром либо считать расширение закрытого enum несовместимым изменением.

**Спорные решения**

- §3: 180 секунд и 600 запросов для одной и той же выборки в A/B/C — агрессивный default. На насыщенном WordPress-сайте бюджет может закончиться до PRIV/CONSENT-05; **⚠ проверить** распределение запросов и p95 времени.
- §6, строка 188 ограничивает извлечение same-origin iframe. Playwright позволяет работать с cross-origin frame через собственный API; такое ограничение необязательно и снижает полезность PRIV.
- Внешняя политика требует дополнительного разрешения scope. Это безопасный выбор, но ссылка на известный внешний legal-документ должна разрешаться адресно без обхода всего внешнего сайта.

## 4. Глубокий разбор по моей линзе

### 4.1. Нужна модель состояния посетителя, а не только названия фаз

У всех предложений `preConsent` используется слишком свободно. Это фактически **«сканер ещё не нажимал CMP»**. Между тем сайт мог автоматически применить consent, получить его через другой механизм или ошибочно считать посетителя согласившимся.

Для каждой страницы нужны независимые поля:

- действие сканера: отсутствует / scroll / legal-navigation / reject / accept;
- состояние CMP: unknown / pending / denied / partial / granted;
- происхождение состояния: default / сохранённое решение / действие / наблюдаемая специальная ветка;
- готовность источника: stub / loading / ready;
- scope решения: origin, домен, CMP-instance и версия конфигурации.

`false` из API-стаба не доказывает отказ. Consent-cookie не доказывает ни согласие, ни бот-режим. Распознанный CMP не доказывает, что его интерфейс управляет всеми загруженными интеграциями.

Особенно важен переход: **клик → pending → наблюдаемое обновление состояния → reload**. Немедленный reload способен оборвать сохранение отказа и создать искусственный дефект. Но запросы между кликом и обновлением нельзя выбрасывать: это отдельное наблюдаемое окно задержки.

### 4.2. Порядок страниц сам изменяет результат

Один профиль A последовательно посещает несколько страниц. После первой загрузки меняются cache, SW, storage и состояние CMP. Поэтому «карта не загрузилась при входе через главную» не доказывает поведение **прямого входа на Kontakt**.

Нужны два понятия покрытия:

- первый визит на сайт по заданному entrypoint;
- последующие переходы в той же сессии без выбора.

Для важных альтернативных entrypoints — Kontakt, лендинг, другой шаблон — предусмотреть адресный свежий A-прогон. Его необязательно выполнять для всех URL по умолчанию, но отсутствие такого измерения должно быть видно.

Выбор C по наблюдениям A особенно опасен: правильно заблокированный YouTube/виджет не породит в A сетевого признака. Выбирать страницы нужно также по плейсхолдерам, DOM и шаблонам, а затем повторять **те же действия** в A/B/C.

### 4.3. «Тишина» ограничивает измерение, но не доказывает отсутствие tracking

Собственный quiet-window лучше `networkidle`, однако имеет ту же фундаментальную границу: таймер на 30 секунд не обязан проявиться за 6–20 секунд.

Исправления:

1. Отсчёт общего page-budget начинается до навигации, а не после `load`.
2. Отдельно фиксируются DOM readiness, CMP readiness и observation duration.
3. Исключение WS/SSE из ожидания не исключает их из анализа.
4. Записываются остановленные запросы, фоновые вкладки и момент ухода.
5. Отрицательный результат формулируется только для конкретного окна и действий.

Повторная загрузка без события не опровергает ранее записанное событие. Репликация оценивает частоту воспроизведения, а не автоматически превращает прямое evidence в слабое.

### 4.4. CONSENT-04: actionability и первый уровень — разные измерения

DSK Rn. 124–125 различает необходимость взаимодействия с баннером и возможность принятия на первом уровне; Rn. 127 не устанавливает универсального стандарта размеров и цветов. Мобильная компоновка также существенна. [DSK OH Digitale Dienste](https://www.datenschutzkonferenz-online.de/media/oh/OH_Digitale_Dienste.pdf).

Алгоритм должен сначала сохранить неизменённый первый экран: viewport, scroll positions, кнопки, видимые тексты, bounding boxes и препятствия. Только затем выполнять действие. Playwright может автоматически прокрутить кнопку перед кликом; успешный клик поэтому не устанавливает её исходную видимость. [Playwright Locator](https://playwright.dev/docs/api/class-locator#locator-click).

Дополнительно:

- `aria-modal=true` само по себе не доказывает фактическую блокировку;
- scroll-lock может относиться к внутреннему контейнеру;
- `elementFromPoint` может вернуть дочерний элемент самой ссылки;
- «Verbergen» или `×` нельзя считать принятием без проверки семантики;
- узнавание CMP и узнавание функции конкретной кнопки должны иметь разные confidence.

Pur-Abo следует распознавать как кандидат на ручную оценку, сохраняя измеренные свойства интерфейса. Простая эвристика «цена + Abo» не должна скрывать обычный дефект.

### 4.5. Bot/geo diagnostics не должны становиться универсальным выключателем

Главный риск Opus/Fable — диагностика, которая слишком легко объясняет любое автоматическое согласие «особым режимом».

Нужна иерархия evidence:

- **наблюдение:** баннер не показан, категории granted;
- **прямой сигнал:** конкретная ветка `isSpider`, ответ геосервиса, документированная конфигурация;
- **гипотеза:** возможно влияние UA или региона.

Только второй уровень позволяет уверенно ограничить интерпретацию человеческого сценария. На третьем нужно сохранять факты и причину неопределённости.

DE-egress предпочтительнее общего EU/EWR для воспроизведения немецкого интерфейса: настройки сайта могут различаться по странам. Proxy должен применяться согласованно к браузеру и связанным HTTP-запросам; иначе DOM политики, TLS и browser-network могут описывать разные региональные ответы.

За upstream proxy нельзя выдавать отдельный локальный DNS-result за фактический `connectedIp`. При отсутствии подтверждения от удалённой точки это поле должно оставаться unknown.

### 4.6. Service workers требуют графа происхождения запроса

Playwright документирует пример, где один URL порождает два context request-события: Frame-owned и SW-owned. Frame-событие не означает отдельный внешний запрос; у SW-request вызов `request.frame()` бросает исключение. [Playwright Service Workers](https://playwright.dev/docs/service-workers).

Следовательно, нужен граф:

> инициатор страницы → обработка SW → cache либо реальный upstream-fetch → ответ странице.

Без этого:

- один контакт посчитается дважды;
- cache-response превратится в утверждение о новой передаче;
- сборщик может упасть при обычной атрибуции frame;
- SW-fetch после навигации потеряет страницу-источник.

SW оставить включёнными в основном прогоне. Диагностический прогон с блокировкой SW должен иметь отдельную маркировку и не подменять результат основного.

### 4.7. CONNECT не закрывает пробел beacons

Новое CONNECT-соединение доказывает соединение с хостом, но не конкретный tracking endpoint. Beacon может уйти по уже существующему туннелю — нового CONNECT вообще не будет.

Нужны:

- подписки до создания/навигации страниц;
- CDP-наблюдение нужных targets с корректным lifecycle;
- отдельная фаза ухода со страницы;
- окно завершения сбора при ещё живом browser context;
- журнал потери target/session;
- специальная проверка корректности времени и attribution последнего запроса.

Для локальных тестов источник истины — журнал принимающего fixture-сервера: что действительно дошло и что сохранил сканер. В production такого oracle нет.

**⚠ проверить** конкретный механизм pagehide/keepalive capture на выбранной поставке Chromium. Утверждение ресёрча «Playwright не видит» нельзя обобщать на все будущие версии и сценарии; одновременно нельзя считать его исправленным наличием proxy.

### 4.8. Consent Mode v2: наблюдать команды, состояние и запросы раздельно

Google прямо предупреждает, что wire-параметры могут изменяться; `gcs` отражает storage consent, а `gcd` отправляется и без включённого Consent Mode. Наличие параметра не доказывает корректную настройку режима. [Google: HTTP parameters](https://developers.google.com/tag-platform/security/concepts/consent-mode#consent_mode_http_parameters).

Обязательные контрпримеры:

- custom dataLayer name;
- замена массива/`push`;
- GTM template consent API;
- несколько defaults с разными регионами;
- более специфичный регион;
- default granted, исправленный до measurement;
- update, поставленный в очередь, но ещё не обработанный;
- consent в iframe и отдельном GTM-container.

Google рекомендует templates использовать специальные consent API, а не `gtag consent`, и предупреждает об очередности команд. Поэтому порядок `push` не равен порядку применения consent. [Google consent templates](https://developers.google.com/tag-platform/tag-manager/templates/consent-apis).

Декодер `gcd` должен быть версионированной capability. Незнакомый формат даёт unknown, а не битовую интерпретацию по старой таблице. Нельзя одной регуляркой по наличию буквы в строке устанавливать эффективное состояние.

### 4.9. Cookieless не означает ни отсутствие данных, ни устойчивую идентификацию

Нужны отдельные признаки:

- measurement event;
- consent-state ping;
- наличие identifier-поля;
- совпадение identifier со storage;
- устойчивость в пределах документа/сессии;
- передача рекламных/пользовательских данных.

Случайный идентификатор на загрузку и устойчивый cookie-derived ID имеют разное доказательное значение. Их сравнение возможно в памяти; экспортировать значения не требуется.

Для sGTM проверять first-party endpoints независимо от eTLD+1. Google поддерживает и поддомен, и same-origin path. [Google: custom domain configuration](https://developers.google.com/tag-platform/tag-manager/server-side/custom-domain).

При этом `/collect`, CNAME, FPID или сходный payload подтверждают лишь признаки интеграции. Дальнейшую серверную пересылку и юридического получателя по ним устанавливать нельзя.

### 4.10. Минимизация должна сохранять доказательную пригодность снимка

Все четыре предложения требуют чистых checks после redaction. Без отдельного слоя извлечения признаков это создаёт конфликт:

- удалён POST-body — потеряны event и признаки endpoint;
- удалён cookie value — нельзя сопоставить его с отправленным ID;
- удалён consent-state — неизвестно, был ли отказ;
- оставлено только имя storage key — неизвестно время операции.

Правильный порядок:

> кратковременное чтение → извлечение разрешённых признаков и корреляции → удаление чувствительного значения → сериализация.

Snapshot должен содержать, например: `identifierPresent`, `matchesStoredIdentifier`, `eventType`, `consentState`, `parserVersion`, `observationSource`. Из безопасного снимка должны воспроизводиться именно эти выводы.

Произвольные `id`, `en`, `ev` нельзя сохранять только потому, что имя параметра попало в allowlist: значение тоже может содержать персональные данные.

### 4.11. PRIV-01/02: отсутствие требует доказательства полноты

`body.textContent` решает проблему свёрнутого текста, но одновременно захватывает:

- неиспользуемые шаблоны;
- старые версии политики;
- скрытый текст другого языка;
- списки услуг, которые сайт никогда не активировал.

Это создаёт **пропуски PRIV-01**, поскольку формальное совпадение найдено в нерелевантном тексте.

Каждый фрагмент должен иметь происхождение: rendered-visible / раскрываемый пользователем / отдельное приложение / скрытый нерелевантный кандидат. Сервис из списка выбора генератора нельзя автоматически считать описанным в действующей Datenschutzerklärung.

Полнота — не число символов. Нужны manifest частей, выбранный язык, завершённость загрузки, найденные приложения, ограничения размера и ошибки разбора. Если сервис не найден, но релевантная часть недоступна, результат — `inconclusive`.

Для PRIV-02 нормализованное утверждение должно включать:

> субъект → предикат → отрицание → условие → область страниц/целей → время.

«Keine Cookies» и «keine nicht notwendigen Cookies vor Einwilligung» — разные утверждения. «Fonts lokal» не опровергается загрузкой другого Google-продукта. «Analyse erst nach Einwilligung» не опровергается событием в C.

Категорийное описание и упоминание компании требуют ручной оценки релевантности. Найденное слово не означает достаточности политики, а ненайденный бренд — установленного нарушения.

### 4.12. TLS-03: разделить исходную ссылку, выбранный ресурс и реальную передачу

Общее деление «пассивное апгрейдится, активное блокируется» слишком грубо. Алгоритм учитывает destination, IP-literal, `imageset` и потенциально доверенные URL; например, imageset имеет отдельное исключение из upgrade. [Mixed Content: алгоритм upgrade](https://w3c.github.io/webappsec-mixed-content/#upgrade-algorithm).

Нужны четыре результата:

1. Небезопасный URL присутствует в исходнике.
2. Браузер выбрал его для загрузки.
3. Он upgraded либо blocked.
4. Действительно состоялась HTTP-передача.

Неиспользуемое CSS-правило, невыбранный `srcset` и скрытый шаблон не равны загрузке. Отдельно учитывать redirects, вложенный HTTP-ресурс HTTPS-iframe, `ws://` и HTTP form action. Форму не отправлять; сообщать о конфигурации action.

CDP Audits/Security/Network должны включаться до загрузки соответствующего target. **⚠ проверить** реальную полноту issues для OOPIF, workers и выбранной browser revision.

### 4.13. LEGAL-01 должен проверять путь пользователя

HTTP GET цели — вспомогательная проверка. Он может получить WAF-страницу, другой язык, пустую SPA-shell или иной региональный ответ при рабочем документе в браузере.

Нужны независимые результаты:

- управляющий элемент найден;
- доступен без принятия;
- действие ведёт к документу;
- документ содержателен;
- путь воспроизводим с данной страницы.

Проверять меню и модалки разрешёнными действиями, не отправляющими формы. Само наличие скрытой ссылки не доказывает доступность; отсутствие ссылки в footer не доказывает недостижимость. §5 DDG требует лёгкой узнаваемости, непосредственной достижимости и постоянной доступности, а не конкретного расположения ссылки. [§5 DDG](https://www.gesetze-im-internet.de/ddg/__5.html).

Страницу с challenge нельзя просто исключать из знаменателя: отчёт должен показывать **запланировано / наблюдалось / удалось оценить**. Иначе «6 из 6» получится после удаления всех неудобных страниц.

### 4.14. Вне браузерной линзы тоже остаются значимые ошибки

- Для HDR нельзя засчитать `frame-ancestors` в meta-CSP как защиту: эта директива там не поддерживается. [CSP: доставка через meta](https://www.w3.org/TR/CSP3/#meta-element).
- Остановка DMARC Tree Walk на eTLD+1 не является полной реализацией RFC 9989; алгоритм может обращаться к PSD. Это касается формулировки Opus и наследования, недостаточно раскрытого Terra. [RFC 9989, §4.10](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.10).
- `Stable tag` WordPress — metadata механизма публикации; его нельзя безусловно превращать в exact runtime-version установленного кода. [WordPress: обработка readme](https://developer.wordpress.org/plugins/wordpress-org/how-your-readme-txt-works/).
- Fingerprint по одному сервису/типу legal-документа способен скрыть новую затронутую страницу. Для baseline нужны значимый scope и правила изменения покрытия.
- Канарейка должна измерять также **abstention rate**: сканер, всегда отвечающий `inconclusive`, не должен выглядеть точным из-за отсутствия ложных critical.
