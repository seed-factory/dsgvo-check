# ADR-0006 — Коды возврата и чистая функция `gate()`

Этот документ фиксирует точную семантику кодов `0/1/2`, флагов `--fail-on` и `--strict` и приоритет причин. Нужен разработке, авторам Action и GitLab-шаблона и пользователям CI.

## Статус

`Proposed` — ждёт ответа заказчика на вопрос 2 «Контракт кодов 0/1/2» ([раздел 8](../consensus/README.md#8-вопросы-заказчику)): нужно подтвердить, что недоступная цель, WAF и таймаут до завершения сбора стартовой страницы дают `2` — это уточнение буквального «сканер сам упал» из ТЗ, — и цену мягкого режима GitLab. D03 — спор 2:1:1, решение модератора в пользу компромисса Opus-К.

## Контекст

- ТЗ: `0` — порог не превышен, `1` — превышен, `2` — сканер сам упал; порог `--fail-on critical|warning`.
- Спор 2:1:1 в раунде 3. Sol-К и Terra-К: любая ошибка включённой проверки → `2`, `2 > 1`. Fable-К: ошибка проверки без `--strict` не даёт `2`. Opus-К: компромисс по релевантности. У первого варианта транзиентный SERVFAIL у MAIL-03 превращается в «сканер упал», хотя при `--fail-on critical` её максимальный вариант (`warning`) порог не достигает, — главный источник флейков. У второго — `exit 0` при `TypeError` в CONSENT-04: зелёный CI при невыполненной P0.

## Решение

`gate()` — чистая функция над готовым отчётом; она даёт предварительный код до репортёров, окончательный фиксируется после них.

**Приоритет:** `2 (fatal)` > `1 (порог)` > `2 (check-error / strict)` > `0`.

- **Fatal:** скан не состоялся — цель недоступна (`SCAN-UNREACHABLE`), WAF или челлендж на стартовой (`SCAN-BLOCKED`), глобальный `--timeout` до завершения фазы A на стартовой (`SCAN-TIMEOUT`), браузер не установлен, sandbox не поднялся при `--sandbox require`, неверные аргументы или конфиг (в том числе override `locked`-варианта), внутренний сбой, не записан JSON или запрошенный HTML, PDF, JUnit, Summary (`report-write-failed`).
- **Порог:** `--fail-on critical` (по умолчанию), `warning` или `none`; «достигнут или превышен», `warning` включает `critical`. Учитывается находка, не подавленная действующим правилом и не покрытая baseline (или с выросшим уровнем).
- **Релевантная проверка:** включена, `gating: true` в ruleset и `maxSeverity ≥ failOn`. `maxSeverity` — статический максимум уровней `variants` после ruleset и overrides (`locked`-варианты не поднимаются), **без кэпа уверенности**: у упавшей проверки уверенности нет, кэп применяется только к конкретной находке. Ошибка релевантной проверки → `2`, если нет `1`. Ошибка нерелевантной проверки на код не влияет.
- Нераспознанный баннер, бот- и гео-режим на код не влияют; `--strict` поднимает их, `SCAN-SANDBOX-OFF` и `egress.region: unknown` при включённых CONSENT-проверках до `2` (если нет `1`).
- **Входы гейта.** Политику задают `--fail-on` и `--strict`. На вход гейта влияют также `--baseline`, файл подавлений, `rules:` (overrides), `--checks`, `--timeout` и `--sandbox off` (через `--strict`).
- **Таймаут после частичного сбора:** незавершённые проверки `error(timeout)`; `1` при учитываемой находке, иначе `2`, если незавершённые проверки релевантны, иначе `0`.
- **`--fail-on none`** выключает только порог `1` и релевантность ошибок проверок; `--strict` действует независимо. Итог: `0`; `2` при fatal или strict-причинах.
- **Окончательный код.** JSON пишется первым как страховка, затем работают остальные репортёры; ошибка любого запрошенного репортёра добавляет `report-write-failed` и даёт `2`. После них JSON атомарно перезаписывается (временный файл и rename) с окончательными `summary.exitCode` и `exitReasons`. Код процесса расходится с JSON, только если не удалась сама перезапись; тогда `2` и сообщение в stderr.
- Все причины пишутся в `summary.exitReasons[]`: `threshold`, `check-error:<id>`, `unreachable`, `blocked`, `timeout`, `sandbox-unavailable`, `invalid-input`, `internal-error`, `report-write-failed`, `strict:inconclusive:<id>`, `strict:sandbox-off`, `strict:egress-unverified`.
- **Мягкий режим — по платформам.** GitHub: `continue-on-error`; если среди причин есть `check-error`, Action печатает `::warning::` и строку в Job Summary. GitLab: `allow_failure: exit_codes: [1]` — только явная документированная опция, не значение шаблона; шаблон печатает все `exitReasons` в stderr, JUnit несёт `<error>`. Цена: при наличии находки job проходит и тогда, когда упала релевантная проверка (вопрос 2).

## Рассмотренные варианты

| Вариант | Плюс | Минус |
|---|---|---|
| Компромисс Opus-К (выбран, решение модератора при споре 2:1:1) | Нет зелёного CI при упавшей P0; флейк нерелевантной проверки не роняет job | Нужны статические `variants` (они и так нужны тесту полноты); при `1` ошибка проверки видна только в `exitReasons` и предупреждении |
| Любая ошибка включённой проверки → `2`, `2 > 1` (Sol-К, Terra-К) | Проще, CI никогда не зелёный при сбое | SERVFAIL у MAIL-03 = «сканер упал»; находка о сайте прячется за кодом инфраструктуры |
| Ошибка проверки по порогу, `2` только по `--strict` (Fable-К) | Буква ТЗ | `exit 0` при исключении в P0-проверке |
| Модель ZAP (`2` = есть WARN) | Знакомо | Несовместимо с ТЗ; в README отдельно объяснить, что наш `2` ≠ ZAP |

## Последствия

- Каждая строка таблицы ситуаций ([§5.2 консенсуса](../consensus/README.md#52---fail-on-и-коды-012)) — табличный тест `gate()`; каждый путь к `2` — контрактный тест с валидным по Ajv отчётом, в том числе минимальная схема `failed`. Отдельно: `--fail-on none --strict`, таймаут до и после стартовой, 429/503 браузера, код процесса = `summary.exitCode` после ошибки HTML-репортёра.
- Отчёт пишется в `finally` с собственным таймаутом; находки, собранные до сбоя, сохраняются при любом коде.
- Смена семантики кодов — major схемы ([ADR-0007](0007-report-schema.md)).
