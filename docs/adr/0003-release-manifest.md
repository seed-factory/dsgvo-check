# ADR-0003 — Release manifest 1.0

Этот документ фиксирует, что входит в релиз 1.0, что идёт следом и что уходит первым при нехватке бюджета. Нужен заказчику для согласования объёма и разработке для планирования этапов 1–4.

## Статус

`Proposed` — ждёт подтверждения заказчика по вопросу 4 «Release manifest» ([раздел 8](../consensus/README.md#8-вопросы-заказчику)): перенос CONSENT-05 из P1 в релиз расширяет ТЗ, а HTML, JUnit и Summary ТЗ не требует («HTML — если успеешь»). D01 — единогласно, D02 — большинство (Terra-К: JUnit только после фиксации кодов — сделано).

## Контекст

- [ТЗ](../../specs/dsgvo-check_TZ.md): «количество проверок — сколько успеешь, порядок P0 → P1 → P2»; HTML — «если успеешь»; обязательны CLI, JSON, коды возврата, Action, GitLab-шаблон, Docker-образ, тесты, README.
- [Каталог](../../specs/dsgvo-check_katalog-proverok.md) содержит 15 P0, 10 P1 и 8 P2. CONSENT-05 (трекинг после отказа) в P1, но без него сценарий «срабатывает ли Ablehnen» из идеи заказчика не закрыт.
- Оценка (D26): 79–94 чд без буфера, 91–108 с буфером 15 %, коридор риска до 135 чд. Каркас этапа 1 («первая проверка каждого модуля») выполнением P0 не считается.

## Решение

| Корзина | Состав |
|---|---|
| Релиз 1.0 | Все 15 P0; CONSENT-05 (перенос из P1); фаза M; форматы JSON, консоль, HTML (один файл без JS), JUnit, GitHub Job Summary; Action, GitLab-шаблон, образ amd64, npm |
| Stretch 1.0 | PDF — `dsgvo-check report report.json --format pdf`, печать того же HTML в офлайн-контексте Chromium; последняя задача этапа 3а, первой уходит |
| Порядок вылета при нехватке бюджета | PDF → JUnit → GitHub Job Summary → HTML. JSON и консоль — контракт ТЗ, не вылетают; фаза M не вылетает (корректность CONSENT-04) |
| Этап 3б (после manifest) | Остальные P1 в порядке каталога: EMBED-03, EMBED-04, EMBED-05, CONSENT-06, VULN-01, VULN-02, MAIL-03, TLS-03, TLS-04; при нехватке бюджета первыми за борт — VULN-01/02 |
| После релиза | P2 (DNS-01, HDR-02, SEC-01, LEGAL-02, BFSG-01, PERF-01); FILE-01 и ADMIN-01 — только как opt-in класса E после правовой оценки заказчика; SARIF, GitLab Code Quality, Catalog-компонент, GeoIP, PDF-политики через pdfjs-dist. Образ arm64 — после нативного smoke (D24), не обязательно после релиза |

Новые ID вне каталога — в бэклог, не в релиз. `en`-тексты выходят в 1.0 только вычитанными ([ADR-0002](0002-product-boundary.md), D22). Прототип по [`docs/prototype/BRIEF.md`](../prototype/BRIEF.md) закрывает сдачу этапа 1, но не является ни релизом, ни его воротами ([ADR-0019](0019-prototype.md)).

## Рассмотренные варианты

| Вариант | Плюс | Минус |
|---|---|---|
| 15 P0 + CONSENT-05 (выбран) | Закрывает все четыре сценария идеи; CONSENT-05 переиспользует фазу B и verify, цена около 3–4 чд | Расширение ТЗ, нужно согласие заказчика |
| Только P0 | Буква ТЗ, минимальный бюджет | «Что меняется после отказа» в релизе не измеряется; CONSENT-04 без CONSENT-05 даёт половину картины |
| Сокращённое ядро с явным списком исключений | Быстрее релиз | Нарушает «P0 — без этого релиза нет» из каталога |
| Все P1 в релизе (Sol-П держал HTML/PDF и полный P1) | Полнее | Оценка Sol-П занижена на 30–40 %; VULN требует четырёх внешних источников данных |

## Последствия

- Этап 3а — 45–52 чд, PDF как stretch уже внутри (без него 44–50); остальные P1 около 20 чд сверх релиза.
- Правовые ворота встроены в план (в редакции модератора): конец этапа 0 — смысл `critical`, политика уровней (T0/T1 «critical-способные», T3 не выше `warning`), коды, UA, manifest, политика `null` для `crmCode`; этап 2 — Impressum и DSE домена проекта; конец 3а — подписанные значения ruleset, маппинг `crmCode` и тексты, стоп-листы, лицензионный аудит; этап 4 — правовой статус в README.
- Оценка пересчитывается после спайков С1–С7 этапа 0.
- Каждый отложенный формат и проверка имеет место в архитектуре заранее: открытые `evidence.type`, `PageProbe` для плагинов BFSG/PERF, `--exposure-probes` для класса E.
